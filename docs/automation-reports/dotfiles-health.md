## Recommendations

### 1. Reject unsupported Copilot installer arguments before doing anything
- Evidence: `ai/copilot/install.sh:4` returns success immediately if the executable exists; `ai/copilot/install.sh:8` checks only the first argument for `--check`. Every other invocation reaches the remote installer at `ai/copilot/install.sh:14`. Consequently, on a missing installation, `--help` or a typo installs when `ALLOW_REMOTE_INSTALLERS=1` is already set, while `--check extra` silently succeeds as a dry-run. The consent gate remains effective (`libexec/lib/artifacts.sh:150`); this is not a consent bypass. Existing tests cover reuse, consent and installer failure, but not argument handling (`tests/copilot_installers.bats:18`).
- Change: validate the complete argument list before the installed-file check. Accept no arguments or exactly `--check`; reject other inputs with usage and exit 2. Optionally support an explicit nonmutating help form. Add roughly 10–15 script lines and 15–25 test lines; no new abstraction is needed.
- Risk: external callers may currently pass ignored arguments. Search those callers before tightening the contract. With a fake downloader, test both present and missing installations and explicit consent: invalid/help invocations must never download, execute, or create directories; ordinary apply and exact check must retain their behavior.

### 2. Remove the completed rollout plan and superseded design, keeping current recovery guidance
- Evidence: `ai/pi/plugin-security-stack-design.md:5` explicitly labels its sandbox, pins, routing and ownership model superseded. The 947-line `ai/pi/permissive-permission-policy-implementation-plan.md:27` still presents work on removed `bin/` maintenance paths as pending tasks. `implementation-notes.md:262` and `implementation-notes.md:282` record the final implementation and successful verification; the current validator actually invokes the resulting pipeline (`libexec/validate-pi-security-runtime.ts:245`). The notes are historical evidence, not a record of this week's checks. Current operational and recovery procedures already live in `ai/README.md:449` and `ai/README.md:455`.
- Change: after confirming no rollout work remains open, remove the superseded plugin design, completed implementation plan and root implementation notes: about 1,831 lines. Retain `ai/pi/permissive-permission-policy-design.md` for the permission policy's rationale and retain current backup/rollback instructions. Remove the obsolete historical-file search exemption in `tests/feature_workflow_policy.bats:64` as part of that separately reviewed cleanup. Git history can preserve the historical account without another tracked archive.
- Risk: an operator or external task may still depend on the old rollout evidence. Confirm canonical rollout status on active hosts, resolve any remaining acceptance tasks, and check private/external references before deletion. Repository search found references among these historical files and the test exemption; the generic instruction to read an `implementation-notes.md` when present is not a dependency on this particular completed record. No migration script or historical rollback procedure should be removed merely because these documents are deleted.

### 3. Make the public update help agree with the lockfile policy

- Change: replace the update target's help comment with “Update packages/runtimes; restore Neovim plugins to the tracked lockfile.” One documentation line replaced; leave the recipe untouched. This file is protected for this automation, so the correction is recommended rather than applied.
- Risk: no runtime behavior changes. Verify the rendered help and retain the README's separate manual `:Lazy update` instructions.
